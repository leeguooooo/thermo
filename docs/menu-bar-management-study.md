# 菜单栏管理与综合工具定位

更新日期：2026-10-22。已有实验性实现和隔离验证；菜单栏实际隐藏效果尚未验收，不代表已交付。

## 产品范围

用户明确希望做 macOS 综合工具，后续会有很多功能。菜单栏管理是其中一个模块。现有 `MenuBarPreferences` 和 `MenuBarData` 管理 Thermo 自身的图标、指标及点击动作，没有隐藏其他应用图标的能力。

综合工具的入口建议采用工具搜索、收藏和分类目录。菜单栏只放收藏的动作与必要状态；各模块按需启动，权限在首次使用对应功能时请求。已有的系统监控、搜索、截图录屏、清理及应用管理共用这些入口，避免每个模块再增加一个常驻图标。

用户进一步明确希望通过扩展配置功能。采用宿主与扩展分离的结构：原生模块提供系统能力，宿主负责配置、入口和生命周期；后续脚本提供者使用单独的运行适配器。

## 已接入的扩展接口

`NativeToolExtension` 提供描述、激活、停用和打开界面四项接口。菜单栏管理已作为 `builtin.menubar` 接入。菜单从宿主读取已启用、允许显示的扩展，设置页提供统一的“扩展…”入口。其他现有工具尚未迁入；尚未实现第三方脚本加载、扩展安装、共享快捷键或命令搜索。

配置文件为 `~/Library/Application Support/Thermo/Extensions/settings.json`，可以在扩展窗口显示并手动编辑，编辑后点“重新载入配置”。例如：

```json
{
  "schemaVersion": 1,
  "extensions": {
    "builtin.menubar": {
      "enabled": true,
      "showInMenu": true,
      "order": 0
    }
  }
}
```

隐藏菜单入口不会停止模块；关闭扩展则会停止工作，并请求恢复图标显示。退出宿主停止已启动模块，保留扩展配置。未知扩展 ID 的配置保留，不能据此加载代码或调用未注册模块。损坏、版本不兼容及超过 64 KiB 的配置不会被重写；已运行模块会停止，原文件留给用户处理。

原生模块仍可拥有功能内的设置。当前扩展开关控制菜单栏模块是否可用；管理窗口里的实验开关控制是否使用系统隐藏接口。第三方脚本适配器后续需要支持明确的命令入口、参数、结果、取消和权限声明，不能通过“能保存扩展开关”就认定扩展平台完成。

## macOS 27 的实现边界

本机实际系统为 macOS 27.0.1（26A434）。不能只完成旧系统分隔符功能便认为满足本机需求。

Ice 2 的[原型记录](https://github.com/teddychan/ice-2/blob/main/docs/testing/macos27-prototype.md)与[集成记录](https://github.com/teddychan/ice-2/blob/main/docs/testing/macos27-integration.md)说明：旧有每个图标对应窗口的模型在其 macOS 27 测试环境中失效。新版使用 Accessibility 发现应用，并通过运行时加载 `MenuBarClientCore` 的私有 assertion 控制显示；按 bundle 管理，不能保证同一个应用的多个图标独立隐藏，也不能直接恢复旧式逐图标捕获、移动和面板能力。

该路径还有系统项目可能随 assessment 模式一起隐藏的副作用。Thermo 若采用，必须实际核对系统图标，并在激活失败、超时、退出、睡眠和权限撤销时恢复显示。不能以私有类或 selector 存在证明可用。

[MenubarHide](https://github.com/junior-rj/menubar-hide)提供另一条公开状态项路线：其 macOS 27 实现通过多个受限宽度的 spacer 将项目挤入系统 overflow，而不是单个 10,000 点分隔符。它与原生按应用隐藏的语义不同。需要对比刘海、窄屏和多屏表现，再决定是否适合作为 Thermo 的折叠方式，不能将 overflow 当成三组逐应用管理。

实现应把持久分组、临时展开状态、系统能力与实际应用结果分开。应用身份不能依赖一次进程的 PID 或伪造窗口 ID。未识别的新应用默认显示；保存但未运行的应用仍能编辑；不支持单项控制的系统图标单列说明。

## 实现与验收顺序

1. 在本机做隔离探针，先验证发现、隐藏测试项目、恢复测试项目。使用独立 bundle ID，不替换安装版、不改变现有分组；同时观察系统图标副作用。
2. 实现稳定身份、三组保存、临时显示隐藏组、显示全部及一键恢复。macOS 27 按应用分组的限制要直接显示在编辑界面。
3. 接入统一工具入口与可编辑分组列表。先确保真实菜单栏里的项目可访问，再实现经验证可行的面板、搜索、快捷键和自动收起。
4. 验证刘海、多屏热插拔、Spaces、睡眠唤醒、权限撤销、应用退出及新应用启动。失败须显示原因并恢复可访问状态，不能只翻转按钮。
5. 核对常驻采样、事件监听与定时器：关闭模块后停止工作；截图和 Accessibility 权限互相独立，不为普通收起功能预先请求全部权限。

自动化检查覆盖分组规则、未知身份、持久化、过期异步回调、超时和恢复。GUI 验收须证明实际图标消失、可重新访问、退出后恢复；纯模型测试或窗口树变化不足以证明像素级效果。

## 品牌提案

建议改显示品牌。Thermo 的语义集中在温度，难以表达综合工具。先选主品牌，温度和风扇保留为系统监控模块；不让主品牌绑定 Bar、Clean 或 Capture。

暂定候选方向是 **Maclio**：短、可读，不限定具体功能；本次关键词检索未确认同名工具产品，但这不证明商标、域名或商店名称可用。正式选定前仍需查重。中文可以另取独立名称，不必音译。

改名应作为单独变更审查。当前 `Resources/Info.plist` 的标识为 `dev.thermo.app`，显示名为 Thermo；helper 标识为 `dev.thermo.helper`，构建脚本绑定现有签名及 Sparkle 账户。优先保持这些身份、偏好与更新验证连续，只改用户可见品牌；DMG、App 路径、登录项、安装器、Homebrew cask、更新源旧地址和权限继承分别做升级验收。显示名改变不等于完成迁移。

## 当前证据与未完成项

已新增 `MenuBarCore` 分组与会话控制、运行时 Objective-C 桥接、管理窗口及原生扩展宿主。实际隐藏默认关闭；持久分组与临时展开分开。请求失败、超时、权限撤销及退出会请求恢复；恢复请求异常时保留句柄，允许再次恢复，不把请求成功当成图标已经恢复。

`scripts/verify-menu-bar.py --output /absolute/new-directory` 会从实际源码构建独立预览和测试图标 App，运行核心测试并保存输入哈希、日志和能力探针。预览使用独立 bundle ID 与配置目录，不替换安装版。正常打开预览后，通过应用菜单的“扩展…”查看配置窗口。

原生接口自检是显式操作：启动同目录的 Fixture App 后，执行预览二进制 `--self-test <fixture-bundle-id>`；目标必须是同一验证目录下的独立测试应用。测试自动请求恢复并移除自己的临时状态项；Fixture 在 120 秒后自行退出。`--observe` 提供 10 秒观察窗口。不能同时运行其他菜单栏管理器。

本机 macOS 27.0.1（26A434）上，桥接类和 selector 检查通过，激活回调无错误，恢复请求无异常。自检未通过“隐藏后应用 AX 节点消失”的判定；独立 Fixture 也仍在 AX 树中。另观察到系统溢出入口在请求期间消失、恢复后重新出现，但 Fixture 原本就在溢出区，尚未取得目标图标的可见位置对照。上述证据不足以证明真实隐藏成功或失败，不能把自检改成只检查回调就宣称通过。

管理窗口的中文布局、无权限状态和恢复入口已通过隔离 GUI 检查。扩展窗口已实际点击启用开关、菜单显示、排序和重载；JSON 读回一致，禁用后“打开”按钮不可用。首次检查发现 SwiftUI 宿主将窗口撑得过高，关闭隐式内容尺寸驱动后，R8 预览已复核为 660×468 点（含标题栏）。普通 LaunchServices 启动的预览没有辅助功能权限，shell 启动的能力探针继承现有运行上下文而显示已授权；两者不可混同。

冻结当前已提交基线并仅叠加本轮文件后，已完成 ThermoApp 编译和 36 项定向测试，涵盖原菜单栏配置、显示逻辑、新分组控制、扩展配置及宿主生命周期。隔离构建另覆盖 20 项核心测试；这些与整合测试有重叠，不能相加为独立覆盖数量。完整记录见 [本轮验证收据](measurements/menu-bar-extension-2026-10-22.json)。

剩余范围包括：实际图标与三组切换、系统图标副作用、退出和睡眠唤醒、多屏及刘海验收；旧系统后端；快捷键、自动收起、搜索入口；第三方脚本提供者和其他模块迁移。尚未改名、替换安装版或发布，目标继续保持未完成。

远程 `leo@192.168.0.190` 本轮报告 `m3b`、macOS 26.5.2，约 795 GiB 可用，只有 Swift 6.3.3／macOS 26.5 的 Command Line Tools，指定 Xcode 27.0 路径不存在。用户随后明确允许使用本地电脑；本轮编译和测试使用本机 Xcode 的 Swift 6.4／macOS 27 SDK，没有更改全局工具链选择。
