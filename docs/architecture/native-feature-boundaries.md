# 原生功能的源码边界

功能中心统一入口和生命周期，源码仍需按职责拆成 SwiftPM target。`ThermoApp` 不能通过共享的 `AppModels` 或 `MainPage` 反过来引用每个功能的模型。只把原有 App 文件整体移到一个新库，不满足 #41。

运行方式沿用 [#54 的修订](https://github.com/leeguooooo/thermo/issues/54#issuecomment-6844730464)：自家功能继续在可信主进程内运行；第三方和不可信内容解析保留沙盒。源码拆分不增加功能进程、原生安装器或可混用版本的动态加载器。

## 目标依赖

```text
ThermoApp -> ThermoComposition
ThermoComposition -> ThermoShell、ThermoKernel、各功能 target
ThermoShell -> ThermoKernel、NativeFeatureAPI、ThermoUI
ThermoKernel -> NativeFeatureAPI、ModuleKit、ModuleHost、内核服务
各功能 target -> NativeFeatureAPI、ThermoUI、各自的业务库
ThermoUI -> ThermoL10n
```

组合层只组装服务和注册功能，不放页面、模型或业务流程。Shell 和内核不能导入功能实现。功能模型和页面保持 target 内部可见；功能之间通过路由和内核拥有的恢复事件协作，不互相取得模型。

`ThermoUI` 只包含样式、通用控件、页面容器和可见性租约，不依赖 AgentDoctor、解析器、权限代理或具体功能。`NativeFeatureAPI` 承载原生功能共用的任务和生命周期契约；沙盒使用的 `ModuleKit` / `ModuleSDK` 不因此增加 SwiftUI 依赖。

## 功能的所有权

每个功能持有当前启用周期内的模型、界面、任务、命令和退出策略。元数据和旧参数解析不创建模型。宿主只取得经过清单校验的功能路由和界面贡献，不接收整个模型容器，也不通过 `Any` 或服务名称查找具体模型。

关闭仍遵守原有顺序：阻止新的 CLI 请求，先检查不可中断的操作；拒绝时保留开关。接受后移除入口、停止接收新工作，等真实读取和命令租约排空，再按实例身份释放缓存。排空期间不能重新开启。watch 正常退出，不发送结束信号。

退出 App 与关闭功能是不同操作。截图的录制收尾、贴图保存和延后退出必须保留；不能用一个通用 `stop()` 替换。helper 管理、安全恢复、权限代理、保护名单、操作账本和撤销批次由内核保留，性能功能关闭后仍可恢复系统控制。

## 实施顺序

1. 提取通用界面与任务代码，保持行为及画面一致。
2. 以连接功能为首个完整单元，迁移模型、页面、后台读取、停止和退出策略；同步迁移窗口、诊断和菜单调用，删除旧的具体模型入口。
3. 逐个迁移其余功能。性能模块迁移前拆开采样与 helper 管理；预览子进程及文件描述符代理的安全边界保持原样。
4. 组合层完成后，删除旧模型总容器和具体页面分支，用实际依赖图及禁止引用检查验收 #41。

比较过独立闭包注册、生成式封闭枚举和动态原生 bundle。采用静态链接、功能各自持有会话的方案；多个独立注册表容易分散同一生命周期，动态 bundle 则增加 ABI、签名、卸载及版本协调。目前用依赖与注册一致性门禁约束组合清单，需要时再引入生成器。

## 验收边界

独立 target 编译和禁止引用检查证明源码边界；生命周期测试证明关闭、排空和重开规则。它们不替代桌面、权限、沙盒或真实服务验收。进程内模块的内存和能耗不能按进程可靠拆分，#42 的显示口径另行定案。

第一步的通用代码提取不代表 #41 已完成，也不改变新安装和老用户升级的开关策略。发布仍随 App/Sparkle 进行。
