# Mole 研究与 Thermo 差异化方向

> 本文只研究公开 CLI。付费原生 App 1.16.0 的 DMG 研究见 [Mole 原生版学习记录](mole-native-study.md)。下文的温度、归因、清理与恢复结论不可套用到原生版；原生版包内已有相关模块及产品状态，具体证据与未验证项见新报告。

分析日期：2026-10-15。只静态阅读 `tw93/Mole` 的公开源码（提交 `81c12fd`，V1.59.1 之后），没有运行其中任何脚本。Mole 的命令行是 GPL-3.0，Thermo 闭源：只借鉴思路，不引入它的代码、规则表或残留数据库。付费原生 App（mole.fit）没有源码，只参考 README 和用户截图。

## 它是什么

- 定位：「CleanMyMac + AppCleaner + DaisyDisk + iStat Menus 合一」，命令是 `clean / uninstall / optimize / analyze / status / purge / installer / history / touchid`。
- 实现：会删除文件的命令全部用 Bash（兼容 macOS 自带的 bash 3.2）；只有 `status`、`analyze` 两个终端界面用 Go。约 7.4 万行。
- 分发：Homebrew 和 `install.sh`。安装脚本校验 SHA256 和 GitHub 构建来源证明，校验不过就直接失败；`mo update` 能识别安装渠道。没有遥测。
- 面向 agent：`CLAUDE.md` 链接到 `AGENTS.md`；skill 写明先 `--dry-run`、破坏性命令由用户执行，并列出五个机器可读入口（`analyze --json`、`status --json`、`status --watch`、`history --json`、dry-run）。

## 值得学的做法

**安全**
- 「判断不了」一律当作「不安全」：进程检查返回三态，查不出来就当在运行；Spotlight 超时就保留。
- 审阅时记下文件的 device:inode:mtime，删除前再核对一次，变了就跳过。
- 父目录是符号链接时也要解析，但解析结果只能用来拒绝，不能用来放行。先过允许名单，再过拒绝名单。
- 白名单文件读不出来就停止整个命令；几条硬性保护规则总是合并进去，用户无法删掉。
- 工具自带清理命令时优先用它（`npm cache clean`、`brew cleanup`、`go clean`）。
- 测量超时时，总量写成「至少 X」，不写成 0。
- 每条日志都带运行编号；`mo history --json` 输出每次运行的统计和删除清单，大小未知时输出 `null`。

**监控**
- 采样分三档：快速档 1 秒、进程 1 秒、完整档 30 秒，快速档沿用上一次完整档的结果，并标注数据是否过期（`process_stale`）。
- 先采 CPU，再启动其他子进程，免得自己的开销算进读数。
- 健康分在阈值之间线性扣分，致命信号直接封顶（SMART 故障时最高 44 分）。顶部一句话诊断会点名占用最多的进程。
- 输出被管道接走时自动改用 JSON；`--watch` 输出 NDJSON，速率类指标持续有效。

**工程**
- 测试用临时 HOME 和会大声报错的命令替身；CI 在多个 macOS 版本上跑，因为命令输出随系统版本变化。
- 有审计脚本：每个原始 `rm` 都必须带 `# SAFE:` 注释；另有危险路径的 fuzz 语料。
- 加新开关和加新设置一样要论证；依赖真实用户数据的决定，先发一个只读探针收集数据。

## 它的短板

- **温度整条链路是坏的。** CPU 温度从来没有赋值，健康分里 15% 的温度权重、「CPU 温度高」的诊断、CPU 卡片上的温度都不会出现，只剩电池温度。Apple Silicon 上的风扇转速来自 `system_profiler` 文本，多半是空的。GPU 占用依赖需要 root 的 `powermetrics`，通常拿不到。
- **没有归因。** 进程按 `comm` 基名排序，只保留前 5 个；Chrome、Electron 的子进程不归并到所属 App，更不知道是哪个项目、哪个 agent 启动的。
- **清理不经审阅。** `mo clean` 扫描完就直接永久删除，还会清空 `~/.Trash`，连卸载功能依赖的「废纸篓可恢复」也一起清掉了。非终端环境下 `purge` 会直接删除所有不是最近修改的项目。除了卸载进废纸篓，没有任何撤销。
- 残留判断的「30 天未使用」看的是目录自身的 mtime，不看里面的内容。日志只保留一份轮转。

## 对照 Thermo

| 方面 | Mole | Thermo |
|---|---|---|
| 温度、风扇 | 基本缺失 | SMC/IOHID 逐个传感器读数，root helper 控风扇，带超温保护 |
| 「为什么慢」 | 健康分，加一句点名进程的诊断 | 判定顺序：热压力 → 磁盘 → 负载 → 内存；进程归并到 App，命令行进程按 cwd 定项目，向上找父进程定 agent |
| 清理 | 直接删除，没有撤销 | 分安全 / 审阅 / 风险三级，需确认；废纸篓批次可单独清空；Claude 重置、标签、agent 修复都可恢复 |
| 操作历史 | 统一日志 + `history --json`，但不能撤销 | **分散在 10 多处、格式各异**：`clean.log`、`fix.log`、batch jsonl、各功能 manifest；没有统一入口，也不能统一恢复 |
| 白名单 | 有，且读不出就停止 | **没有持久白名单** |
| 维护任务 | `optimize` 19 项 | 只有隐私页的 DNS 刷新 |
| 卸载应用 | 进废纸篓，有已测试的残留规则 | 进废纸篓，但**没有批次号** |

## 差异化方向

Thermo 不追功能广度，而是把 Mole 做不到的两件事做深：

1. **热与原因（第一期）。** 概览页回答「为什么热、是谁、怎么办」：顶部一句话结论，点名来源（哪个 App，或哪个项目里的哪个 agent）；中间一条「负载 → 温度 → 风扇 → 降频」的热链路，哪一环出了问题就突出哪一环，风扇操作就在那一环上；下面按来源列出占用。Mole 的温度缺失、没有归因，正是这一块。
2. **可恢复的操作历史（第二期）。** 把分散的记录汇总到一个日志里，提供 `thermo history --json` 和一个历史页，每一条都链接到对应的恢复入口。Mole 有历史但不能撤销；Thermo 本来就能恢复，只是没有统一出来。
3. 小项：持久白名单（读不出就停止）、卸载和空间透视加上批次号、清理时优先用工具自带命令。
